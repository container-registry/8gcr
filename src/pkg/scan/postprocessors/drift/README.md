# Scan report persistence drift suite

Pins what users see from stored scan reports, so a change to how reports are written
(`postprocessors.toSchema`, the `vulnerability_record` DAO, record cleanup) can be checked for
drift. The golden files were recorded on the implementation before the batched write path.

## What a scenario observes

Each `capture` step records, normalized (record ids replaced by their key, run-specific ids,
digests and names replaced by labels, rows sorted, strings over 512 bytes hashed):

| | Observation | Serves |
|---|---|---|
| O1 | `FromRelationalSchema` per artifact and scanner | vulnerabilities API, pull block, CVE allowlist |
| O2 | `report.GenerateSummary` plus the `scan_report` counters | scan overview, artifact list, webhook payload |
| O3 | Security Hub DAO: summary, top-5 lists, vulnerability list and counts | `/security/summary`, `/security/vul` |
| O4 | `export.Manager.Fetch` | CVE CSV export |
| O5 | stored records per key, links per report, unlinked records | database state |

Not compared, on purpose:

- The order of findings in a report: `GetForReport` has no `ORDER BY`, and the order already varies
  between runs of the same implementation with the query plan.
- Which tied row makes a Security Hub top-5 list: recorded by ordering values only.
- Unlinked records after a `cleanup` step: the cleanup exists to change them. With a cleanup in
  place the suite asserts that none are left.
- Error texts: a step records only `ok` or `error`.

`rows_unchanged: true` on a capture records whether any record or link row was written since the
previous capture (by comparing `xmin`), which pins "an identical rescan writes nothing".

## Scenarios

`testdata/scenarios/*.yaml`, one sequence of `register_scanner`, `scan` (inline `report`,
`report_file` under `testdata/reports`, or a verbatim `raw_report`), `delete_artifact`,
`delete_scanner`, `cleanup`, `concurrent` (steps run in parallel) and `capture` steps. s09, s18 and
the report files are generated by `testdata/gen_fixtures.py`.

Scenarios that pin current defects say so in their description: s04 (a fix-version-only change is
not stored), s05 (a rescan does not update the CVSS v3 vector), s10 (the first of two duplicate items wins), s11 (a finding whose `cve-package-version`
string collides with another is dropped, marked `known_bug` with the fixed expectation; any drift fails,
and the message says when the fixed expectation holds), s13 (a
score of 0 from vendor attributes without a score), s22 (an update drops a vendor-derived score).

s19 (`TestDriftLarge`, `DRIFT_LARGE=1`) scans an 8k CVE report against 200k preloaded records,
pins the result by hash, and writes the cost of each phase to `testdata/baseline/s19-<name>.json`
(`DRIFT_BASELINE_NAME`, default `current`): wall time, peak live heap, statements and rows from
`pg_stat_statements` when the extension is loaded, and the plan of the lookup.

## Running

```bash
# Postgres with pg_stat_statements for the s19 statement counts
docker run -d --name scan-drift-pg -p 127.0.0.1:5442:5432 -e POSTGRES_PASSWORD=root123 \
  -e POSTGRES_DB=registry postgres:19-alpine -c shared_preload_libraries=pg_stat_statements
export TZ=UTC POSTGRESQL_HOST=127.0.0.1 POSTGRESQL_PORT=5442 POSTGRESQL_USR=postgres \
  POSTGRESQL_PWD=root123 POSTGRESQL_DATABASE=registry \
  POSTGRES_MIGRATION_SCRIPTS_PATH=$PWD/make/migrations/postgresql
cd src/pkg/scan/postprocessors/drift
go test -tags db -count=1 .                    # compare with the golden files
DRIFT_LARGE=1 go test -tags db -count=1 -run TestDriftLarge -timeout 30m .
go test -tags db -count=1 . -update            # record, only for a reviewed, deliberate change
```

Every scenario runs twice per test and both runs must agree, which proves the normalization
leaves nothing run-specific.

## Applying it to a new implementation

Run the suite unchanged against the new code. Any golden diff is drift; a deliberate behavior
change is re-recorded with `-update` and its diff reviewed in the same PR. The API-level replay
of the same scenarios against a running Harbor is in `tests/scan-drift`.
